# consolinho operations runbook

How to deploy, upgrade, back up and troubleshoot `consolinho` (FleetConsole) on OpenShift. The audience is operators.
Design background: ADR-0026 (image), ADR-0027 (migrations), ADR-0028 (production hosting), ADR-0029 (security
headers), ADR-0030 (manifests, configuration contract, dev script) in `docs/adr/`.

> [!WARNING]
> **Data Protection keys: losing either the Data Protection certificate (Secret `consolinho-dp-cert`) or the
> `data_protection_keys` table makes every stored ServiceAccount token unreadable.** Every cluster credential then has
> to be entered again by hand. Back up **both**, and keep old certificates after a rotation.
> See [Data Protection keys — read this](#8-data-protection-keys--read-this).

All examples use placeholders (`example.com`, `REPLACE_ME`). Never paste real tokens, passwords or kubeconfigs into
tickets, chat or this repository.

## 1. Overview

One namespace (`consolinho`) holds:

| Object | Purpose |
|---|---|
| Deployment `consolinho` | Pod = init container `migrate` (applies EF Core migrations, then exits, ADR-0027) + container `server` (API + SPA on port 8080). Rolling update `maxUnavailable: 0`, `maxSurge: 1`. |
| Service + Route `consolinho` | Edge TLS, HTTP→HTTPS redirect, HSTS, `haproxy.router.openshift.io/timeout: 330s` for watch streams. The Route host is copied from `Console__PublicOrigin`. |
| ServiceAccount `consolinho` | No RBAC, no token automount. The pod needs no cluster permissions. |
| NetworkPolicies `consolinho-ingress` / `consolinho-egress` | Ingress only from the router on TCP 8080; egress only DNS (53/5353), TCP 5432, 443, 6443. |
| ConfigMap `consolinho-config` | Non-secret settings (generated by kustomize, name has a hash suffix). |
| Secrets `consolinho-db`, `consolinho-oauth`, `consolinho-dp-cert`; ConfigMap `consolinho-ca-bundle` | Created by the dev script or the operator, never by kustomize. |
| OAuthClient `consolinho` | Cluster-scoped; created by the dev script or the operator, never by kustomize. |

The **dev** overlay (`deploy/kustomize/overlays/dev`) adds a single Postgres StatefulSet `postgres` (dev only), the
ServiceAccount `consolinho-smoke` with a namespaced `view` RoleBinding, and (through `deploy/kustomize/build`) the
BuildConfig/ImageStream `consolinho`. The **production** overlay (`deploy/kustomize/overlays/production`) sets
2 replicas and a PodDisruptionBudget (`minAvailable: 1`) and expects an external Postgres.

## 2. Prerequisites

- `oc` logged in to the target cluster with rights to create the namespace and namespaced objects, and to create
  **OAuthClients** (cluster-scoped): `oc auth can-i create oauthclients` must print `yes`.
- Tools: `oc`, `openssl`, `git`, `tar`, coreutils. `podman` only to build or check the image locally
  (`scripts/check-image.sh`).
- The cluster's router namespace carries the label `policy-group.network.openshift.io/ingress` (the default on
  OpenShift); the ingress NetworkPolicy relies on it.
- Production only: an external PostgreSQL (16 recommended) and a registry the cluster can pull from.

## 3. First dev deploy

For a test cluster you may reinstall at any time. Everything is derived from the current `oc` login.

```bash
oc login https://api.cluster.example.com:6443      # as a user who may create OAuthClients
scripts/deploy-dev.sh                              # asks [y/N], naming the API URL
scripts/deploy-dev.sh --yes --admin alice          # non-interactive; alice becomes the bootstrap admin
scripts/deploy-dev.sh --help
```

**Flags:** `--yes` (skip the deploy confirmation), `--admin <user>` or `--admin=<user>` (bootstrap admin, default:
`oc whoami`; the script warns for `kube:admin`, which disappears once the cluster has an identity provider),
`--teardown`, `-h|--help`. The namespace is fixed to `consolinho`. Output is a checklist (`✓ …` per step; `! …`
warnings and `✗ …` errors on stderr, exit ≠ 0). Requires `oc auth can-i create oauthclients` = `yes`.

**What the script derives and creates:**
- API URL and user from `oc whoami`; apps domain from `ingresses.config/cluster`, so the console is at
  `https://consolinho.<apps domain>` (`Console__PublicOrigin`).
- Secrets, **created only if missing**: `consolinho-oauth` (random client secret), `consolinho-postgres` and
  `consolinho-db` (random DB password), `consolinho-dp-cert` (self-signed Data Protection certificate + password, see
  [§4.4](#44-data-protection-certificate)). Values go through a temporary directory and `--from-file`; they are never
  printed or put on a command line.
- ConfigMap `consolinho-ca-bundle` = the namespace's `kube-root-ca.crt` + `openshift-config-managed/default-ingress-cert`.
  A copy for the smoke steps is written to `${XDG_CACHE_HOME:-$HOME/.cache}/consolinho/ca-bundle.crt`.
- An in-cluster binary build (`oc start-build consolinho --from-archive`) of the **working tree** (tracked and
  untracked-but-not-ignored files, so uncommitted changes are deployed; ignored files never are). The build log goes
  to `${XDG_CACHE_HOME:-$HOME/.cache}/consolinho/build.log` (its tail is printed on failure).
- A gitignored overlay `deploy/kustomize/overlays/.dev-generated/` (public origin, bootstrap admin, built image digest,
  version label = git short SHA, `-dirty` if the tree has changes), applied with `oc apply -k`.
- OAuthClient `consolinho` (see [§4.6](#46-oauthclient); server-side apply, labelled `app.kubernetes.io/part-of:
  consolinho`), then waits for `oc rollout status` (300 s). It finishes with the Console URL, the bootstrap admin and
  the smoke steps below. On failure it prints where to look (`oc logs deploy/consolinho -c migrate`, `oc describe pod -l app.kubernetes.io/component=server`).

**Re-runs are idempotent:** generated secrets are read back from the cluster, so a second run only builds a new image,
rewrites the generated overlay (image, version) and rolls the Deployment.

**Teardown (humans only):** `scripts/deploy-dev.sh --teardown` needs an interactive terminal (it refuses piped
stdin) and `oc auth can-i delete oauthclients`; it asks you to type the namespace (`--yes` does not skip this), deletes the OAuthClient `consolinho` and the project `consolinho` (database, DP certificate and all stored
credentials are gone). The local CA bundle copy stays.

### 3.1 Smoke test: the host cluster as a managed cluster (SMK-1)

The script prints these steps at the end; it never creates or prints the token.

1. `oc create token consolinho-smoke -n consolinho --duration=168h` — copy the token.
   *Token lifetime:* 168 h outlives a test cluster and shows the `exp` in the UI. If the API server caps or rejects
   that duration, run the command without `--duration` (the default lifetime is short, typically one hour) and rotate
   the credential with a fresh token when it expires.
2. In the console: Fleet administration › Clusters › **Register** with the API URL the script printed, the CA bundle
   file `${XDG_CACHE_HOME:-$HOME/.cache}/consolinho/ca-bundle.crt`, environment `dev`.
   If the external API URL serves a custom named certificate, append its CA to that file first (`kube-root-ca.crt`
   covers only the cluster's own API certificates).
3. Add a credential with the token and **Test** it.
4. Grant your user ReadOnly on the cluster, switch to it and open Pods in project `consolinho`.

### 3.2 Widening the smoke ServiceAccount (SMK-3, manual)

`consolinho-smoke` can only `view` the `consolinho` namespace. To browse the whole cluster read-only, a human may
bind `cluster-reader`. This creates a **cluster-scoped** ClusterRoleBinding, which is why the script never does it:

```bash
oc adm policy add-cluster-role-to-user cluster-reader -z consolinho-smoke -n consolinho
# undo — do this BEFORE --teardown: the ClusterRoleBinding survives the namespace deletion
oc adm policy remove-cluster-role-from-user cluster-reader -z consolinho-smoke -n consolinho
```

## 4. Production deploy

Nothing in production is derived from `oc`; every value is set by the operator.

### 4.1 Image

Build the image from the repository root and push it to your registry (ADR-0026):

```bash
podman build -f deploy/Containerfile --build-arg REVISION="$(git rev-parse HEAD)" \
  -t registry.example.com/consolinho/consolinho:1.0.0 .
podman push registry.example.com/consolinho/consolinho:1.0.0
```

Base images are `registry.access.redhat.com/ubi9/{nodejs-22,dotnet-100,dotnet-100-aspnet}:9.9` (anonymous pulls,
RHEL-minor stream tags that receive .NET/z-stream rebuilds; bump all three together when a new UBI minor ships). The
build needs egress to `registry.access.redhat.com`, the npm registry and nuget.org (or your mirrors).

Optional local gate before pushing: `scripts/check-image.sh` (needs `podman`, `openssl`, `curl`; ~5 min cold) builds
its own `localhost/consolinho:check` and runs it like restricted-v2 (random UID, group 0, read-only root, `/tmp` only):
image content, `migrate`, SPA/probes/headers and the fail-fast exit codes. `--no-build` reuses the last build.

### 4.2 Overlay

Copy `deploy/kustomize/overlays/production` next to it (e.g. `deploy/kustomize/overlays/acme-prod`) in your own
checkout or configuration repository. If the copy does not sit next to `base`, point `resources:` at the base with a
correct relative path or a pinned remote base (`https://<git host>/<repo>//deploy/kustomize/base?ref=<release tag>`).
Do not move the `replacements:` stanza: it must stay in the outermost kustomization.

Replace these placeholders in `kustomization.yaml`:

| Placeholder | Set to |
|---|---|
| `images[0].newName` / `newTag: REPLACE_ME` | Your image, e.g. `registry.example.com/consolinho/consolinho` + `1.0.0`, or `digest: sha256:…` instead of `newTag` |
| `app.kubernetes.io/version: REPLACE_ME` | Release label (informational, never in selectors) |
| `Console__PublicOrigin=https://consolinho.apps.cluster.example.com` | The public `https` origin, no trailing slash. It becomes the Route host and the OAuth redirect URI base. |
| `Auth__BootstrapAdminUsers__0=REPLACE_ME` | The OpenShift user name (exact) of the first administrator |
| Optional: `Auth__AdminGroups__0` | An OpenShift group whose members are administrators |
| `namespace: consolinho` | Keep it unless you have a reason; all commands below assume `consolinho` |

`overlays/production/secrets.example.yaml` documents the Secrets below with fake values. It is **not** referenced by
the kustomization; never fill it in and commit it.

### 4.3 External PostgreSQL (DB-4)

Sections 4.3–4.6 write secret files. Work in a private directory and remove the files once they are stored in the
cluster (and in your offline backup, for the DP certificate):

```bash
umask 077; mkdir -p ~/consolinho-secrets; cd ~/consolinho-secrets
```

Production uses a managed or DBA-run PostgreSQL; the dev Postgres is a single pod with no backups and is not
supported in production. Ask for an empty database (e.g. `consolinho`) and a role that **owns** it (the `migrate` init
container creates and alters tables). `migrate` would create a missing database itself, but only if the role has
`CREATEDB`; in production let the DBA provision it. Reachability: the egress NetworkPolicy allows TCP **5432** only — if your
database listens on another port, add that port to `consolinho-egress` with a patch in your overlay.

Use TLS with certificate verification in the Npgsql connection string:

```
Host=db.example.com;Port=5432;Database=consolinho;Username=consolinho;Password=REPLACE_ME;SSL Mode=VerifyFull
```

`SSL Mode=VerifyFull` checks the chain and host name against the system trust store of the image; if the database
uses a private CA, add `Root Certificate=<path>` and mount that CA file into the pod with an overlay patch.

Write the connection string with the real password into the file `connection-string` **with an editor** (never
`echo`/`printf` it on the command line: it would land in your shell history). Then:

```bash
oc new-project consolinho        # or: oc create namespace consolinho
oc create secret generic consolinho-db -n consolinho --from-file=connection-string=connection-string
rm connection-string
```

### 4.4 Data Protection certificate

The key-encryption certificate protects the Data Protection key ring that encrypts every stored SA token. Generate
it once (the same commands the dev script uses) and **keep a copy offline** (see [§8](#8-data-protection-keys--read-this)):

```bash
openssl rand -hex 32 | tr -d '\n' > password     # a trailing newline would be ignored anyway
openssl req -x509 -newkey rsa:3072 -nodes -days 3650 -subj /CN=consolinho-data-protection \
  -keyout dp.key -out dp.crt
openssl pkcs12 -export -inkey dp.key -in dp.crt -out certificate.pfx -passout file:password
oc create secret generic consolinho-dp-cert -n consolinho \
  --from-file=certificate.pfx=certificate.pfx --from-file=password=password
rm dp.key dp.crt                 # certificate.pfx + password are the backup; store them offline
```

The certificate must carry an **RSA** private key (the startup check refuses others). The 10-year validity avoids an expired-looking certificate in tools; plan rotation by policy, not by expiry ([§8.2](#82-rotating-the-certificate)).

### 4.5 OAuth client secret and CA bundle

```bash
openssl rand -hex 32 | tr -d '\n' > client-secret   # no trailing newline: the env value is not trimmed
oc create secret generic consolinho-oauth -n consolinho --from-file=client-secret=client-secret
```

The CA bundle **replaces** the system trust store for the host API (`https://kubernetes.default.svc`) and the OAuth
route. It must contain:
1. the cluster's `kube-root-ca.crt` (trust for `kubernetes.default.svc`);
2. the CA that signs the OAuth route `oauth-openshift.apps.<domain>`: the ingress CA if the cluster uses the default
   self-signed ingress certificate, **or the public root CA** if the ingress/OAuth route uses a publicly trusted or
   corporate certificate (a public root is *not* implicitly trusted once a bundle is set).

```bash
oc get configmap kube-root-ca.crt -n consolinho -o jsonpath='{.data.ca\.crt}' > ca-bundle.crt
oc get configmap default-ingress-cert -n openshift-config-managed -o jsonpath='{.data.ca-bundle\.crt}' >> ca-bundle.crt
# custom/public ingress certificate: append its root CA instead of (or in addition to) the line above
# cat corporate-or-public-root.pem >> ca-bundle.crt
oc create configmap consolinho-ca-bundle -n consolinho --from-file=ca-bundle.crt=ca-bundle.crt \
  --dry-run=client -o yaml | oc apply -f -
```

Check the OAuth route against the bundle before deploying:

```bash
openssl s_client -connect oauth-openshift.apps.cluster.example.com:443 -CAfile ca-bundle.crt </dev/null 2>/dev/null \
  | grep 'Verify return code'          # expect: 0 (ok)
```

### 4.6 OAuthClient

The cluster-scoped OAuthClient name must equal `Auth__OpenShift__ClientId` (`consolinho`), its `secret` must equal the
`consolinho-oauth` Secret, and its single redirect URI is `<Console__PublicOrigin>/api/auth/callback`. The heredoc
feeds the secret through stdin, not the command line; **server-side** apply keeps it out of the
`last-applied-configuration` annotation that a plain `oc apply` would write (the dev script does the same):

```bash
oc apply --server-side --field-manager=consolinho-operator -f - <<EOF
apiVersion: oauth.openshift.io/v1
kind: OAuthClient
metadata:
  name: consolinho
  labels:
    app.kubernetes.io/name: consolinho
    app.kubernetes.io/part-of: consolinho
secret: "$(cat client-secret)"
grantMethod: auto
redirectURIs:
  - https://consolinho.apps.cluster.example.com/api/auth/callback
scopeRestrictions:
  - literals:
      - user:info
EOF
rm client-secret
```

`grantMethod: auto` skips the consent page (the console only asks for `user:info`); `scopeRestrictions` keeps the
client from ever obtaining a broader token.

### 4.7 Apply and verify

```bash
oc kustomize deploy/kustomize/overlays/acme-prod | less     # review the render (no Secrets in it)
oc apply -k deploy/kustomize/overlays/acme-prod
oc rollout status deployment/consolinho -n consolinho --timeout=300s
oc get route consolinho -n consolinho -o jsonpath='{.spec.host}{"\n"}'   # must equal the PublicOrigin host
oc logs deploy/consolinho -n consolinho -c migrate                       # applied migrations
```

Open the public origin, log in as the bootstrap admin, then register clusters in Fleet administration.

## 5. Configuration reference

Environment variable names are .NET configuration keys with `__` as the section separator (ADR-0030). Startup
error messages use the `:` form of the same keys (`DataProtection:KeyEncryptionCertificatePath` =
`DataProtection__KeyEncryptionCertificatePath`).

| Key (env) | Meaning | Default / value in manifests | Required | Source |
|---|---|---|---|---|
| `ASPNETCORE_ENVIRONMENT` | Hosting mode. `Production` everywhere, also on dev clusters (fail-fast config, no dev endpoints). | `Production` | yes | base ConfigMap; set directly on `migrate` |
| `Console__PublicOrigin` | Public `https` origin, no trailing slash. OAuth redirect URI base and Route host. | placeholder | yes | overlay ConfigMap |
| `Auth__OpenShift__HostApiServerUrl` | Host cluster API for user identity calls. | `https://kubernetes.default.svc` | yes | base ConfigMap |
| `Auth__OpenShift__ClientId` | OAuthClient name. | `consolinho` | yes | base ConfigMap |
| `Auth__OpenShift__ClientSecret` | OAuthClient secret. | — | yes | Secret `consolinho-oauth` key `client-secret` |
| `Auth__OpenShift__CaBundlePath` | PEM bundle that replaces system trust for host API + OAuth route. | `/etc/consolinho/ca/ca-bundle.crt` | optional in code, always set by the manifests | base ConfigMap |
| `Auth__AutoProvision` | Create unknown OpenShift users at first login (without grants). `false` = users must be added by an admin first. | `true` | no | base ConfigMap |
| `Auth__BootstrapAdminUsers__0..N` | OpenShift user names that are admins (evaluated at each login). | placeholder | no in code; set one | overlay ConfigMap |
| `Auth__AdminGroups__0..N` | OpenShift groups whose members are admins (evaluated at login; virtual groups like `system:authenticated` are refused). | — | no | overlay ConfigMap |
| `ConnectionStrings__consoledb` | Npgsql connection string. | — | yes (server and `migrate`) | Secret `consolinho-db` key `connection-string` |
| `DataProtection__KeyEncryptionCertificatePath` | PKCS#12 certificate (with private key) that encrypts the Data Protection key ring. | `/etc/consolinho/dp/certificate.pfx` | yes outside Development | base ConfigMap |
| `DataProtection__KeyEncryptionCertificatePasswordPath` | File holding the PFX password (a trailing newline is ignored). | `/etc/consolinho/dp/password` | no (manifests set it) | base ConfigMap |
| `DataProtection__PreviousKeyEncryptionCertificatePath` | Retired certificate, used **only to decrypt** keys after a rotation. | — | no | overlay ConfigMap, [§8.2](#82-rotating-the-certificate) |
| `DataProtection__PreviousKeyEncryptionCertificatePasswordPath` | Password file of the retired certificate. | — | no | overlay ConfigMap |
| `ASPNETCORE_HTTP_PORTS` | Listen port. | `8080` | — | image (`ENV`; the image also clears `ASPNETCORE_URLS`, which would override it — don't set it) |

**Mounted paths** (all read-only except `/tmp`):

| Path | Content | From |
|---|---|---|
| `/etc/consolinho/ca/ca-bundle.crt` | CA bundle | ConfigMap `consolinho-ca-bundle` key `ca-bundle.crt` |
| `/etc/consolinho/dp/<key>` | Every key of the Secret (`certificate.pfx`, `password`, during a rotation also `previous-certificate.pfx`, `previous-password`), mode `0440` | Secret `consolinho-dp-cert` |
| `/tmp` | The only writable path (`emptyDir`, 256 Mi) | — |

**Dev only:** Secret `consolinho-postgres` (`database-user`, `database-password`, `database-name`) feeds the Postgres
StatefulSet.

Changing a value in the generated ConfigMap renames it (hash suffix), so `oc apply -k` rolls the pods automatically.
Changing a **Secret** or `consolinho-ca-bundle` does not: run `oc rollout restart deployment/consolinho -n consolinho`.

## 6. Upgrade and rollback

Migrations are **forward-only** (ADR-0027): the `migrate` init container applies pending migrations on every pod start
and never runs down-migrations.

**Upgrade:**
1. [Back up](#7-backup-and-restore) the database (and confirm you have the DP certificate backup).
2. Set the new image in the overlay (`images:` `newTag` or `digest`) and the version label; `oc apply -k <overlay>`.
3. `oc rollout status deployment/consolinho -n consolinho --timeout=300s`. The new pod migrates first; with
   `maxUnavailable: 0` the old pods keep serving until it is ready. During the rollout the old pods briefly run
   against the new schema. Concurrent `migrate` runs (several new pods) are serialised by a Postgres advisory lock;
   later ones find nothing pending. On a fresh database the first run logs an EF error about the missing
   migrations-history table before creating it: harmless.
4. If the new pod stays in `Init:Error`/`Init:CrashLoopBackOff`, read `oc logs <pod> -n consolinho -c migrate`. The
   old pods are still serving; fix the cause or roll back.

**Rollback:**
- Re-apply the overlay with the previous image tag/digest (preferred over `oc rollout undo`, which leaves the overlay
  and the cluster out of sync).
- Roll back the image only if the old version works on the new schema (the release notes say so, or the upgrade added
  no migrations: the `migrate` log lists the applied names).
- Otherwise: `oc scale deployment/consolinho -n consolinho --replicas=0`, restore the backup taken in step 1
  ([§7](#7-backup-and-restore); **everything written since that backup is lost**), apply the overlay with the old
  image (this restores the replica count).

## 7. Backup and restore

Back up **two things together**: the database (includes the `data_protection_keys` table) and the Secret
`consolinho-dp-cert`. One without the other cannot decrypt the stored SA tokens.

**Database, production** (run from a host that can reach the DB; use a `pg_dump` at least as new as the server):

```bash
pg_dump -Fc -d "host=db.example.com dbname=consolinho user=consolinho sslmode=verify-full" -f consolinho-$(date +%F).dump
```

**Database, dev** (in-namespace Postgres; the dump streams to your machine):

```bash
oc exec -n consolinho statefulset/postgres -- pg_dump -Fc consolinho > consolinho-$(date +%F).dump
```

**DP certificate** (both environments; store encrypted and offline, never in git):

```bash
umask 077; mkdir -p dp-backup
oc extract secret/consolinho-dp-cert -n consolinho --to=dp-backup
```

**Restore:** a restore **loses everything written since the backup** (users, grants, credentials, audit entries).
Before `pg_restore --clean`, take a fresh `pg_dump` of the current state (as above) so you can go back.

```bash
oc scale deployment/consolinho -n consolinho --replicas=0
# production
pg_restore --clean --if-exists --no-owner -d "host=db.example.com dbname=consolinho user=consolinho sslmode=verify-full" consolinho-2026-01-01.dump
# dev
oc exec -i -n consolinho statefulset/postgres -- pg_restore --clean --if-exists --no-owner -d consolinho < consolinho-2026-01-01.dump
# DP certificate, if the Secret was lost (same key names)
oc create secret generic consolinho-dp-cert -n consolinho \
  --from-file=certificate.pfx=dp-backup/certificate.pfx --from-file=password=dp-backup/password
oc scale deployment/consolinho -n consolinho --replicas=2     # dev: 1, or re-apply the overlay
```

The key ring is bound to the application's fixed Data Protection application name, not to the namespace or cluster,
so a restore into a new namespace or cluster works as long as both the table and the matching certificate are
restored. Restoring an older dump under a newer image is fine: `migrate` applies the missing migrations.

HA Postgres operators, continuous archiving and point-in-time recovery are the DBA's/managed service's concern and out
of scope here.

## 8. Data Protection keys — read this

Stored SA tokens are encrypted with ASP.NET Data Protection. The keys live in the `data_protection_keys` table; each
key is itself encrypted with the certificate mounted from `consolinho-dp-cert`. Therefore:

- **Losing the certificate** (Secret deleted, namespace torn down, no offline copy) → the keys can't be decrypted.
- **Losing the table** (database dropped or restored from a backup without it) → the tokens can't be decrypted.
- Either way every cluster credential must be re-entered. There is no recovery.

### 8.1 What to back up

The database (see [§7](#7-backup-and-restore)) and `certificate.pfx` + `password` — **including every retired
certificate** that is still configured as "previous".

### 8.2 Rotating the certificate

New keys are encrypted with the current certificate; existing keys stay encrypted with the certificate that was
current when they were created. The retired certificate is therefore configured as *previous* (decryption only).

1. Back up the database and extract the current Secret (`oc extract secret/consolinho-dp-cert --to=dp-old`).
2. Generate a new certificate and password as in [§4.4](#44-data-protection-certificate) (into a separate directory,
   `dp-new/`).
   **Do steps 3 and 4 back to back.** A pod that restarts in between loads the new certificate as current without
   a previous one, so old tokens can't be decrypted until step 4 is applied (nothing is lost, but credentials fail
   in the meantime).
3. Replace the Secret with **both** certificates (same Secret, so the existing volume mounts all four files).
   Server-side apply (or `oc replace -f -`) is required: a client-side `oc apply` would copy both PFX files and
   passwords into the `last-applied-configuration` annotation, which `oc describe` and `oc get -o yaml` show:
   ```bash
   oc create secret generic consolinho-dp-cert -n consolinho \
     --from-file=certificate.pfx=dp-new/certificate.pfx --from-file=password=dp-new/password \
     --from-file=previous-certificate.pfx=dp-old/certificate.pfx --from-file=previous-password=dp-old/password \
     --dry-run=client -o yaml | oc apply --server-side --force-conflicts --field-manager=consolinho-operator -f -
   ```
4. In the overlay's `consolinho-config` literals, enable the two rotation keys (already present as comments in
   `overlays/production/kustomization.yaml`):
   ```
   - DataProtection__PreviousKeyEncryptionCertificatePath=/etc/consolinho/dp/previous-certificate.pfx
   - DataProtection__PreviousKeyEncryptionCertificatePasswordPath=/etc/consolinho/dp/previous-password
   ```
   `oc apply -k <overlay>` (the ConfigMap change rolls the pods). The current-certificate keys keep their paths.
5. Verify: pods ready, and **Test** an existing credential in Fleet administration (it decrypts an old token).
   A startup failure names the misconfigured key (`Startup configuration error: …`).
6. Back up the new certificate offline next to the old one.

**Keep the previous certificate configured as long as keys it encrypted remain in `data_protection_keys`** — in
practice indefinitely, because old keys are retained and old tokens may still depend on them. Drop it only if the key
ring is re-created from scratch and every SA token re-entered. Only **one** previous certificate can be configured, so
a second rotation would orphan the keys of the oldest certificate: do not rotate again unless the key ring is
re-created and all SA tokens re-entered.

## 9. Troubleshooting

Look first at `oc get pods -n consolinho`, `oc describe pod -l app.kubernetes.io/component=server -n consolinho` and
`oc logs deploy/consolinho -n consolinho -c server` (JSON lines; request URLs are never logged in Production).

| Symptom | Cause | Fix |
|---|---|---|
| Login lands on `/login?error=unavailable` ("Can't reach the cluster's sign-in service") | The server can't reach or doesn't trust the host API or OAuth route: CA bundle misses `kube-root-ca.crt` or the OAuth route's CA (public root when the ingress uses a public/corporate certificate), or egress is blocked. | Rebuild the bundle ([§4.5](#45-oauth-client-secret-and-ca-bundle)), verify with `openssl s_client … -CAfile`, then `oc rollout restart deployment/consolinho`. Check the server log at the time of the login (trace id). |
| OpenShift login page shows an error instead of the login form, mentioning the redirect URI / `invalid_request` | `redirect_uri` mismatch: `Console__PublicOrigin` + `/api/auth/callback` differs from the OAuthClient's `redirectURIs`, or the Route host differs from the origin (custom Route edit). | Make all three agree: fix `Console__PublicOrigin` and re-apply (the Route host follows it), update the OAuthClient ([§4.6](#46-oauthclient)). |
| `/login?error=not_registered` | `Auth__AutoProvision=false` and the user doesn't exist in the console (also applies to bootstrap admins). | An admin adds the user, or set `Auth__AutoProvision=true` in the overlay and re-apply. |
| No administrator left (all demoted/deactivated) | Admin roles are managed in the UI; the last one was lost. | Set `Auth__BootstrapAdminUsers__0=<openshift user>` (a user that isn't deactivated) in the overlay, `oc apply -k` (rolls the pods), and log in as that user: configuration admins are applied at login. Remove the entry later if you want UI-only admins. |
| Pod `Running` but `0/1` ready, Route returns 503 | Readiness `/health` includes the database: DB unreachable, wrong credentials, TLS verification fails, or the DB listens on a port other than 5432 (egress policy). Liveness `/alive` doesn't check the DB, so the pod isn't restarted — also when the server container (re)starts during the outage: it listens at once, loads the Data Protection key ring in the background (warning `Loading the Data Protection key ring in the background failed` is expected then) and turns Ready by itself once the DB is back. A *new* pod waits in `Init` (the `migrate` init container retries) until the DB is reachable. | Check the server log for Npgsql errors; verify `consolinho-db`, DB firewall/`pg_hba`, port (patch `consolinho-egress`), then `oc rollout restart` after Secret changes. |
| Watches/logs drop with 504 after a while | The Route timeout is shorter than the stream (annotation missing or lowered), or an external load balancer in front of the router has a shorter idle timeout. | Keep `haproxy.router.openshift.io/timeout: 330s` (the proxy caps watches at 300 s); raise the external LB idle timeout above 330 s. |
| Build fails pulling base images, `npm ci` or `dotnet restore` | No egress from build pods to `registry.access.redhat.com`, the npm registry or nuget.org; proxy not configured. | Check the cluster proxy (`oc get proxy cluster -o yaml`, builds inherit it), allow those hosts or use mirrors; alternatively build locally with podman and push ([§4.1](#41-image)). |
| Pod stuck in `Init:0/1` for about a minute, then `Init:Error` / `Init:CrashLoopBackOff` | The `migrate` init container failed (DB unreachable, missing privileges, a failing migration). Against an unreachable DB it fails only after ~60 s, because EF Core retries the connection (6 retries) before giving up. Old pods keep serving. | `oc logs <pod> -n consolinho -c migrate`: one Critical line `Database migration failed: <exception type>: <message>` (never the connection string). Fix and let kubelet retry, or roll back ([§6](#6-upgrade-and-rollback)). |
| Server container exits (code 1, `CrashLoopBackOff`) right after start, one log line per problem `Startup configuration error: <message>` | A required setting is missing or invalid: connection string, DP certificate (`… is required outside Development`, `… points to a file that does not exist`, `… could not be loaded as a PKCS#12 (PFX) file with the password from …`, `… without an RSA private key`; same for the *Previous* keys), `Console:PublicOrigin` or `Auth:OpenShift:*`. The message names the key (`:` form), never the value. | `oc logs <pod> -c server --previous \| grep 'Startup configuration error'`; fix the named key in the ConfigMap/Secret ([§5](#5-configuration-reference)) and re-apply or restart. |
